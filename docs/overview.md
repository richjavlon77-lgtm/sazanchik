# Sazanchik CITY — обзор системы

QR-меню + мини-POS ресторана «Сазанчик CITY» (Ташкент). Гость сканирует QR
на столе, заказывает с телефона; персонал ведёт заказы на своих досках;
менеджер управляет меню, финансами, складом и персоналом.

**Стек:** Next.js (App Router) · Neon Postgres (drizzle) · Vercel · Tailwind ·
vitest. Прод: https://sazanchik.vercel.app

## Контуры и роли

| Контур | URL | Роль | Вход |
|---|---|---|---|
| Гость | `/` | — | без входа, стол из подписанного QR (`?t=`) |
| Официант | `/waiter`, `/waiter/bills` | waiter | PIN |
| Бар / Кальян / Кухня / Холодный цех / Мангал | `/bar` `/hookah` `/kitchen` `/cold` `/meat` | своя роль | PIN (общий экран `/staff`) |
| Менеджер | `/admin/**` | manager | пароль |
| Signage | `/tv` (экран в зале), `/print` (меню для печати), `/print/qr` (QR-карточки) | `/print*` — manager | — |
| Доставка | `/delivery` — мини-апп из Telegram-бота: без зала/официанта, корзина → заявка менеджеру | — | — |
| Telegram-бот | @Sazanchik_city_bot — гость: меню/бронь/доставка; staff/admin/owner-команды по ролям | роли в `tg_users` | приглашения-коды |

Защита в **три слоя**: `proxy.ts` (middleware) → гард страницы/лейаута
(`lib/area-guard.ts`, route group `app/admin/(panel)`) → проверка роли внутри
каждого server action. Мутации никогда не полагаются на middleware.

## Поток заказа

1. Гость (или официант через `createManualOrder`) отправляет корзину.
2. `resolveTable` — стол из подписанного HMAC-токена QR (`lib/table-sign.ts`);
   подделать номер стола в ссылке нельзя. `REQUIRE_TABLE_TOKEN=1` включает
   строгий режим.
3. `priceOrder` — **серверное ценообразование**: цены клиента только
   сверяются с БД (`lib/pricing-core.ts` — чистая математика, покрыта
   тестами). Скидка ДР −10%, сервис +20%.
4. Заказ + позиции пишутся **в одной транзакции**; идемпотентность по
   `idempotencyKey` (partial unique index) гасит двойные сабмиты.
5. Заказ цепляется к открытому счёту стола (`table-session`, race-safe).
6. Списание склада по рецептам (`stock-deduct`, транзакционно, best-effort).
7. `pg_notify` → SSE (`/api/staff/stream`) → доски персонала обновляются живьём.
8. Telegram-уведомление (сбой не роняет заказ).

Отмена заказа (`advanceOrder`) — атомарный check-and-set + возврат склада.
Закрытие счёта (`closeBill`) отказывает, пока по столу есть готовящийся заказ.

## Данные меню — кто источник правды

**БД** (правится в админке). Гостевая `/`, `/tv` и `/print` читают БД;
статический `data/menu.ts` — только аварийный фолбэк при недоступности БД
(и исходник для сидинга). Не редактировать статику в расчёте на прод.

## Два канала заказов

- **Зал**: гость сканирует QR стола → сайт `/` → заказ на стол (сервис +20%),
  несёт официант, счёт закрывается в панели официанта.
- **Доставка**: бот → мини-апп `/delivery` (или корзина прямо в чате бота) →
  телефон+адрес → заявка в `delivery_requests` + рабочий Telegram-чат с
  позициями и итогом (цены сверяются с БД), менеджер перезванивает.

## Отзывы

- Общий отзыв: секция «Оцените нас» внизу главной — ⭐1–5 + комментарий
  ≤100 симв.; публикация только через админку «Отзывы» (модерация).
- Оценка блюда: «Оценить ★» в карточке — публикуется в средний рейтинг
  блюда сразу (`/api/dish-ratings`, кэш 60с), Telegram не спамится.

## Telegram-бот

`lib/tg/`: handlers (роутер+роли), booking-fsm / delivery-fsm (чистые
диалоги), delivery-menu (корзина в чате), menu-browser (витрина с фото),
api (обёртка Bot API). Роли: guest → staff → admin → owner; приглашения —
одноразовые deep-links (`/invite_staff`, `/invite_admin`), владелец — код
`TG_OWNER_CODE`. Webhook `/api/telegram/webhook` (секрет в заголовке);
переустановка: `node scripts/telegram-setup.mjs`.

## Печать и полиграфия

- `/print` — люкс-меню (обложка без логотипа), `/print?lang=uz|en|tr`.
- `/print/qr?count=35` — QR-карточки столов: трим 90×125 мм, вылеты 2 мм,
  метки реза, 2×2 на A4. VIP-кабины (33–35 → «VIP 1–3») — `lib/tables.ts`.
- PDF из терминала: `node scripts/print-pdf.mjs menu|qr [count] [out.pdf]`.
  ⚠️ QR для типографии генерировать ТОЛЬКО с прода
  (`BASE_URL=https://sazanchik.vercel.app`) — подпись стола зависит от
  секрета сервера, локальная подпись в зале невалидна.

## Известные ограничения

- **Rate-limit в памяти инстанса** (`lib/rate-limit.ts`) — на N инстансах
  Vercel лимит фактически ×N. При росте трафика переносить в Redis/Upstash.
- **Варианты порций и склад**: рецепт привязан к блюду, вариант масштабирует
  его через `dish_variants.stock_factor` (поле «Коэф. склада» в админке;
  по умолчанию 1). Вариант линии определяется по её цене — при двух
  вариантах с одинаковой ценой берётся первый по sortOrder
  (`lib/stock-factor.ts`).
- **SSE переподключается каждые ~60 с** (`maxDuration`), каждое staff-устройство
  держит прямое соединение к Neon — следить за лимитом соединений.
- **Фото блюд** лежат base64 в Postgres (`uploads`, отдаются через
  `/api/img/:id` с immutable-кэшом) — Vercel Blob store НЕ подключён
  (токена нет ни локально, ни в Vercel). При текущих ~18 фото / 2МБ это
  нормально; при росте — подключить Blob (`vercel blob store add`) и
  мигрировать, код загрузчика Blob уже поддерживает.
- В `data/menu.ts` нет турецких переводов (в БД колонки `*_tr` есть) — при
  фолбэке TR-гость видит русский.

## Команды

```bash
npm run dev / build / start
npm test              # vitest, 178 юнитов (деньги, QR, i18n, FSM бота, корзины)
npm run lint && npx tsc --noEmit
npm run seed          # сидинг БД из data/menu.ts
npm run db:generate / db:push   # drizzle-kit
node scripts/print-pdf.mjs menu # PDF меню (см. выше)
npm run e2e           # 22 сценария на одноразовом Postgres (прод не трогается)
```

CI (GitHub Actions): lint → typecheck → tests + e2e на каждый push/PR.

## Схема БД

Схема ведётся через `drizzle-kit push` (прод — Neon). Файлы в `drizzle/` —
снимки истории схемы, а НЕ применяемые миграции: `drizzle-kit migrate`
запускать нельзя (0002 — догоняющий снимок, его таблицы в проде уже есть).
Новые колонки применять `db:push` (или точечным ALTER) и генерировать
снимок `db:generate` для истории.
